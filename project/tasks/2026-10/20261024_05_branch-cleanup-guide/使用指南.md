## 3. 打开工作空间

1. 点击顶部或空画布上的“打开文件夹”。
2. 在目录窗口中选择运行器机器上的目录，核对显示的机器和环境。
3. 当前部署只批准了 `/home/workspace/DevFlower/development/model-admission-cas-fix`。先选择这个目录。
4. 打开后核对顶部完整路径、Development 环境，以及左侧发现的会话。

打开目录只读信息，不会启动 Agent。其他项目需要部署者另行登记允许目录和权限；当前安装不能直接在任意文件夹执行任务，也不会因此获得 CodeWeave 的修改权。

## 4. 先用会话，再搭工作流

左侧支持按 Provider 或“Workflow → 节点 → 会话”分类，也可搜索名称、筛选会话/归档/回收站。点击已有会话，会在中央打开对话页签。

- 默认阅读用户输入、助手回答和 Markdown。工具活动和实际请求默认折叠。
- “结构化执行结果”是已完成节点的真实输出，区别于原生文本消息，也不是审核批准。
- 同一个节点与侧栏会话使用同一原生身份。外部导入、原环境不明或占用不明的会话可能只能查看。
- 点击新建会话的加号，选择执行配置、模型、强度和 Ask/Plan/Agent 工作方式。

**模型目录不等于可执行许可。**

1. 点击“刷新模型”，查看来源、更新时间、是否旧缓存及查询错误。
2. 选择当前已登记的模型、effort 和工作方式。
3. 点击“验证执行”，阅读说明并填写“执行验证确认意见”，再点击“确认并验证执行”。这会产生一次实际原生诊断调用，可能计费，但不发送项目源码或任务。
4. 成功后才有当前精确配置的短期执行准入。有效期为 5 分钟；成功业务回执可续验同一配置。模型、强度、模式、Profile、权限、超时或运行配置改变，过期或真实调用失败，都可能要求重新验证。
5. 输入消息，点击发送，在权限预览中确认本次操作。

本次实际验证过的请求配置是 Codex `gpt-6.1-sol/xhigh` 和 Claude Code `claude-opus-5-5[1m]/high`；以后以当前部署批准的配置及真实探测为准。中转站未证明的物理后端和生效 effort 仍是 unknown。目录里看见模型，不代表该账号必然能执行它。

Ask/Plan 由运行器限制为只读；Agent 的写入范围仍受部署与当次授权限制。

## 5. 配置可视化工作流

建议先从顺序示例理解界面，再搭建自己的流程。示例仍需真实 Agent 配置和授权，不会自动产生模拟结果。

1. 新建工作流，或在“示例”中选择顺序、并发汇合、循环或规则路由。
2. 从节点库添加输入、Agent、条件/路由、汇合、循环、人工确认、输出或结束节点。
3. 拖动节点调整位置，从上游右侧端口连接到下游左侧端口。
4. 点选 Agent，在右侧检查器中配置名称、职责、Provider/Profile、会话、模型、effort 和工作方式。
5. 在“提示词”页分别填写初始化提示词、每轮提示词、输出与交接要求。在高级设置中限制权限、超时、预算和输入/输出字段。
6. 点连线，选择实际要交接的字段。上游内容作为数据输入，不会授权下游获得更多工具或路径权限。
7. 填写画布下方“本次任务”，保存工作流，再点击“开始运行”。
8. 核对目标、权限、调用预算和冻结配置，填写确认意见后启动。存在人工确认节点时，还需在运行到该节点后填写对应回答。

初始化提示词在每个新运行的该节点首次执行时发送一次；同一运行的循环、暂停恢复和页面刷新不重复初始化。已有原生会话保留原历史，新运行仍有自己的初始化语义。

常用画布操作：

| 操作 | 方法 |
|---|---|
| 移动节点 | 拖动卡片 |
| 平移/缩放 | 空格或中键平移，滚轮缩放 |
| 适应画布 | 点击画布工具栏相应按钮 |
| 多选、复制、删除 | 使用工具栏或节点右键菜单 |
| 对齐、分布、撤销、重做 | 使用画布工具栏 |
| 添加下游节点 | 从端口拖到空白处，再搜索节点 |
| 插入节点 | 点击连线旁加号 |
| 浅色/深色 | 顶部切换，或跟随系统 |
| 调整阅读空间 | 拖动左右侧栏、底部区域的边缘，或收起面板 |

设计草稿和运行快照是两份内容。运行中的画布固定于启动时的版本；要改下一次流程，先返回“编辑草稿”。

## 6. 看清运行状态与真实交接

开始后，查看画布顶部总览和各节点的状态、轮次、耗时、等待对象、完成数量及失败原因。箭头交接效果来自已记录的后端事件；动画不代表审核或交付通过。

**检查上游传了什么：** 在运行快照点选连线，打开“数据传递”，查看来源/目标节点、来源/目标轮次、实际字段、实际内容、发送/接收状态，以及关联产物和哈希。草稿预览没有真实执行证据。

**检查下游收到了什么：** 点选下游 Agent 的“实际运行”，依次看：

1. 初始化提示词和初始化状态。
2. 每轮提示词。
3. 当前轮上游输入，汇合时保留各来源。
4. 输出与交接要求。
5. 最终组装的可见请求。
6. 原生 Provider 回执、会话和退出状态。

Provider 不提供的字段显示 unknown。界面记录了实际发送的请求，不等于能证明中转站内部每一步处理。

条件节点只按声明字段和确定规则判断；路由未命中时走已配置的默认分支或明确停止。未选分支应显示已跳过。汇合等待声明的输入，循环最多五轮，达到上限应明确停止。

这些能力有自动化测试，但当前最终候选的真实顺序验收曾因 Claude 超时失败，真实汇合补证未继续，不能据此承诺所有真实模型流程已经稳定验收。

## 7. 暂停、停止、关闭和原生终端

| 操作 | 实际含义 |
|---|---|
| 暂停 | 停止调度新节点，当前已启动的进程继续 |
| 继续/恢复 | 核验现有运行和进程后继续；不会自动重放结果不明的调用 |
| 停止工作流 | 取消本任务拥有的执行进程 |
| 关闭配置、交接面板或对话页签 | 关闭显示，不删除原生历史，不停止工作流 |
| 关闭终端视图/标签 | 断开显示，不等同于结束 CLI |
| “关闭此终端” | 明确结束该终端进程，原生历史保留 |
| DevFlower 归档/回收站 | 本软件的可恢复分类，不冒充 Provider 原生操作 |

Escape 关闭最上层浮层并恢复焦点。未保存草稿或未发送消息出现提示时，可选择保存、丢弃或取消。浏览器中的消息草稿依赖本机浏览器存储，不等于已经提交为任务档案。

在已有会话页签选择“原生终端”→“打开同一原生会话”，核对 cwd、HOME/Profile、Provider 和配置后确认。工作台按明确 UUID 恢复，不用猜测最近会话。会话被工作流或其他终端占用时拒绝第二写入者。首次进入原生 CLI 可能出现它自己的配色或目录确认，需要实际处理。

刷新页面恢复同一运行的显示，不应重新启动 Agent。网络错误显示“状态待确认”；先查询和核验，勿连续点击新建运行。终端画面缓冲只在服务内存中，不是永久终端录像。

## 8. 原来的“研发记录”现在在哪里？

**原功能保留了，但研发台账、运行事件和原生会话尚未成为一条自动归档流水线。**

| 记录层 | 记录内容 | 本机位置 | 是否自动同步云端 |
|---|---|---|---|
| 项目研发档案 | 目标、方案、真实授权、实施、自验、独立审核、结论、按时间的过程 | `records/project/`，对应 `project/devflower` | 需要明确整理、提交和 push；不会随每次聊天自动发生 |
| 工作流运行记录 | 冻结图、运行/节点/轮次、状态事件、请求、交接、原生回执 | 当前入口的 `stage-final-r2/storage`，含 `workbench.sqlite`、`usable.sqlite` 等 | 默认仅本地 |
| 原生会话与详细证据 | Codex/Claude 原生历史、原始输出、截图、测试日志、固定候选 | 当前任务的 `native-homes` 和各任务 `archives/` | 按现行约定留本地，不推 Git |
| 源码历史 | 文件改动、commit、PR、合并历史 | `DevFlower` 及 Development 工作树 | 已推送的源码分支在 GitHub |

现有项目台账入口：

- `records/project/STATUS.md`：当前关口和下一步。
- `records/project/AGENT_CONTEXT.md`：接手所需的上下文和指针。
- `records/project/INDEX.md`：按任务日期、顺序、模式和状态导航。
- `records/project/tasks/YYYY-MM/YYYYMMDD_序号_任务名/README.md`：每个任务一份五节记录。
- 同目录 `task.json`：任务状态与源码版本引用。
- Git 提交历史：查每次档案修改；运行事件的时间和序号：查实际执行顺序。

当前源码仍提供 `init/new/index/check`。工作台会保存运行证据，但没有实现“任意一次 Studio 运行结束后，自动生成完整五节任务档案、审阅隐私并提交到 project 分支”的通用闭环。当前 Development 部署的验证/交付外部执行器配置为空，也不能通过添加一个交付节点就自动 commit/push/PR。

因此，保留 `project/devflower` 很有必要。它保存人的目标、取舍和阶段结论；原生聊天和数据库保存执行细节。只保留聊天会缺少整理过的决策，只保留 README 又会缺少细节证据。两者应通过源码 commit/tree、候选哈希、任务/运行/轮次以及原生会话身份相互引用。

这里的可追溯性依赖文件、数据库和 Git 历史被妥善保存，并不等于已部署防篡改的合规审计系统。公开仓库里的所有分支均可见，project 分支不是隐私隔离。

## 9. 今天怎样继续按原来的方式记研发过程？

最简单的方法是让当前研发 Agent 同时维护项目档案。任务开始时说明：

> 在 project/devflower 建立本任务，记录目标、范围、验收和源码基线。实施中追加关键决定和失败证据。结束时整理五节 README、源码身份、测试、独立审核和交付状态，更新 INDEX/STATUS；原始日志和会话留本地，公开前检查隐私。

需要自己操作时，在**记录工作树**中执行：

```bash
cd /home/workspace/DevFlower/records
python3 -B tools/devflower.py new my-task --mode B
```

它会建立按日期编号的任务目录并更新 INDEX，不会提交或推送。把五节 README 填好；在 `task.json` 中更新真实状态和 `source_refs`，不要把自测通过写成独立审核或用户验收。然后执行：

```bash
python3 -B tools/devflower.py index
python3 -B tools/devflower.py check
```

检查只是结构检查，不是正确性批准。最后审阅 `git diff`，按明确文件路径暂存、提交，再正常推送 `project/devflower`。不要把数据库、私有链接、认证、原生会话全文或原始大日志一并加入 Git。

查过去的记录可先读 INDEX，再进入对应任务。需要查看档案随时间的改动，可在记录工作树执行：

```bash
git log --date=iso-strict --format='%h %ad %s' -- project/tasks
```

`project/codeweave` 继续保留 CodeWeave 的研发记录，本次没有改动。项目分支接收经过审阅的框架更新，不把整个项目记录合回 main。

## 10. 对产品方向的建议

建议把“可追溯研发档案”重新放到产品主流程中心：任务卡是入口，画布负责执行，会话负责交流，时间线连接授权、方案、源码、测试、审核、修复和 PR，任务结束再形成可审阅的归档。

下一项值得优先补齐的是“任务结束 → 生成待审档案 → 检查敏感内容 → 人确认或明确授权 → 同步 project 记录”的界面闭环，并支持从档案反查运行/会话证据。这是建议的后续工作，**本轮没有实现，也不能把它描述成现成功能**。

不建议为了减少分支而删除 project/*，也不建议把每条聊天都直接提交进 Git。保持一任务一份清晰结论、必要机器证据，以及本地原始记录即可。
